# UX — LucidaFetcher

Reviewed 2026-09-21. The UI is a React app under `src/ui/`; findings here are about behaviour the user can observe, not visual design.

The status vocabulary in `src/engine/status.mjs` is genuinely good — "Searching Qobuz (wording 2 of 2)", a distinct `READY` state rather than a lie about downloading, and per-outcome abandon reasons. Most of what follows is where that care doesn't reach the end of the wire.

---

### [Medium] The speed limiter can switch itself off and never tell the user

**Where:** `main.js:1340-1344` sends `throttle-unsupported`; no listener exists in `src/ui/`
**Trigger:** A server that will not honour a range request, so a throttled `resume()` restarts the transfer from zero.

**Detail:** The limiter detects this correctly and disables itself for the rest of the session rather than looping forever:

```js
throttleSupported = false;
logEvent('download.throttle.unsupported', { ... });
if (mainWindow && !mainWindow.isDestroyed()) mainWindow.webContents.send('throttle-unsupported');
```

The comment at `main.js:1307-1313` says it "tells the renderer to say so". Nothing in the React UI listens on that channel — `grep -rn "throttle-unsupported" src/` returns nothing. The legacy `renderer.js` does handle it, so this was dropped in the React port.

**Impact:** The Settings speed limit keeps displaying a value that has silently stopped applying, for the rest of the session and for every subsequent download. A user who set a limit to keep their connection usable has no way to find out it is off except by reading the session log.

**Fix:** Listen for the channel in `App.jsx` alongside the existing `tray-command` listener and raise a toast; ideally also disable or annotate the speed-limit field in Settings for the remainder of the session.

**Confidence:** Verified

### [Medium] The concurrency slider commits on every intermediate value

**Where:** `src/ui/views/SettingsView.jsx:131-138`

**Detail:** `onChange` on `<input type="range">` fires for every step of a drag. Each step runs the full commit path: `patch()` → `setLocal` + `setConfig` + an IPC `set-config` (which writes `state/config.json` and logs a `settings.change` event) → `controller.setConcurrency(n)` → `ensureWorkerViews` → possibly constructing new `Worker` objects and new `<webview>` elements.

Dragging 1 → 6 therefore performs five config writes, five log events, and creates webviews for every intermediate value. Dragging 3 → 1 → 3 additionally triggers the slot-collision bug documented as the first finding in `01-bugs.md`.

**Impact:** Config write amplification, log noise that dilutes the diagnostics report, webview churn — and a data-corruption bug reachable by an ordinary gesture.

**Fix:** Keep `value` in local state on `onChange` for the label, and commit on `onMouseUp` / `onKeyUp` / `onBlur`. The same pattern applies to the `maxTransfers` slider below it and to the Jamendo client ID field, which currently sends `set-config` on every keystroke (`SettingsView.jsx:110-111`).

**Confidence:** Verified

### [Medium] A failure during boot leaves the app on the splash screen forever

**Where:** `src/ui/App.jsx:28-44`

**Detail:**
```js
useEffect(() => {
  let cancelled = false;
  (async () => {
    const cfg = isElectron ? await ipc.invoke('get-config').catch(() => ({})) : { ... };
    ...
    await initEngine({ config: cfg, log: ... });
    if (!cancelled) setReady(true);
  })();
  return () => { cancelled = true; };
}, []);
```
The `get-config` invoke is guarded, and `initEngine` guards `controller.restore()` internally — but the async IIFE itself has no `.catch()`. Anything `startEngine` throws (a missing `#worker-views` container, a webview that fails to construct, a throw inside `attachPersistence`) rejects the IIFE, `setReady(true)` never runs, and `<Splash />` renders "Starting the download engine…" indefinitely with no error, no retry and no way forward.

The trigger is narrow — `#worker-views` is present in `src/ui/index.html` — which is why this is Medium rather than High. It is the failure mode for a whole class of startup bug.

**Impact:** An unrecoverable, uninformative hang at launch. The one user-visible surface where the app's otherwise-excellent diagnostics tell them nothing.

**Fix:** `.catch((e) => setError(e))` on the IIFE and render a failure state with the message and a "Save diagnostics" button.

**Confidence:** Verified

### [Low] "Retry missing" silently does nothing the second time

**Where:** `src/engine/controller.mjs:351-366`, button at `src/ui/views/QueueView.jsx:61`

**Detail:** `retrySkipped()` sets `rec.retried = true` and skips any record that already has it, so a track gets exactly one extra pass per session. That is a deliberate guard against a retry loop and the test at `controller.test.mjs:187` pins it. But the UI presents an always-enabled button, and the second press returns 0 with no explanation of why.

**Impact:** The button appears broken. A user whose network has since come back has no way to ask again short of restarting the app.

**Fix:** Either disable the button once every skipped track has `retried` set (with a tooltip saying so), or let the count reset when the user explicitly asks a second time — the loop guard exists to stop *automatic* retries, not deliberate ones.

**Confidence:** Verified

### [Low] Changing the download folder through `set-config` is silently ignored

**Where:** `main.js:494-499` vs `main.js:471-474`

**Detail:** `set-config` merges whatever the renderer sends into `config`, then `saveConfig()` immediately overwrites one field:
```js
function saveConfig() {
  config.downloadPath = downloadPath;   // module-level var, not the patched value
  writeJson(CONFIG_FILE, config);
}
```
So `ipc.send('set-config', { downloadPath })` can never change it. In practice the only writer is `select-directory` (`main.js:1187-1196`), which sets the module variable first, and `pickFolder` in Settings calls that — so the visible flow works. But `pickFolder` then *also* calls `patch({ downloadPath: dir })`, which sends a `set-config` that does nothing, and any future code that tries to set the path this way will fail silently.

**Impact:** None today; a trap for the next change.

**Fix:** Have `set-config` handle `downloadPath` explicitly (validate and assign the module variable), or reject the key and log it.

**Confidence:** Verified

### [Low] No feedback that a scan-based "already downloaded" match is a guess

**Where:** `main.js:884-896` (`checkDownloaded`, `via: 'scan'`), surfaced through `downloads-check`

**Detail:** The folder-scan fallback matches on title tokens only — `want.every((t) => have.indexOf(t) !== -1)` — with no artist check and no exact-match requirement. A file named `Dark Essence (Remix).flac` satisfies a want of `["dark","essence"]`, so the wanted original is marked already-downloaded and never fetched.

The code is honest about this: the setting is off by default and the comment at `main.js:836-840` calls it a guess. But when it does fire, the result reaching the UI is indistinguishable from a manifest hit — same `done: true`, and the track simply does not appear in the queue.

Note `restore()` passes `{ scan: true }` unconditionally (`renderer-integration.mjs:206`), with a good justification, so this path runs on every launch regardless of the setting.

**Impact:** A track silently never downloaded, with nothing on screen saying why.

**Fix:** Carry `via` through to the UI and label scan-derived skips distinctly ("found a similarly named file"), with the filename shown so the user can judge it.

**Confidence:** Verified

### [Low] Windows reserved device names are not handled in folder sanitisation

**Where:** `main.js:867-880` (`folderFor`), `src/engine/sources.mjs:12-14` (`sanitizeFolder`)

**Detail:** Both strip illegal characters, trailing dots and spaces, and `.`/`..` — thorough on everything except Windows' reserved device names. A playlist named `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9` or `LPT1`–`LPT9` produces a path that `mkdirSync` cannot create on Windows, and `writeReport` bails out with only a log line (`main.js:1010-1013`).

`AUX` is a plausible playlist or album name; the rest are unlikely.

**Impact:** A whole playlist fails to download, with the reason only in the session log.

**Fix:** Append `_` to a segment matching `/^(con|prn|aux|nul|com[1-9]|lpt[1-9])$/i`, in both sanitisers.

**Confidence:** Verified (by reading; not reproduced on this machine)
